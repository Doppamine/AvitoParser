## Шаг 2. Модели

**`Apartment`** — наша квартира: `title`, `address`, `avito_url` (blank),
`realtycalendar_id` (blank), `min_nights` (default 2), `is_active`, `created_at`.

**`Competitor`** — объявление конкурента: `apartment` (FK, cascade), `url`,
`title` (blank — заполнит парсер фазы 2), `min_nights` (**null**, на страницах
Avito его нет), `is_active`, `created_at`.
`UniqueConstraint(apartment, url)`.

**`PriceSnapshot`** — замер:

| поле | тип | примечание |
|---|---|---|
| `competitor` | FK, null, **PROTECT** | поправка 3 |
| `apartment` | FK, null, **PROTECT** | поправка 3 |
| `price_kind` | `listing` / `dated` | **новое** |
| `check_in` | date, null | null только у `listing` |
| `nights` | int, null | null только у `listing` |
| `price_per_night` | `Decimal(10,2)`, null | |
| `total_price` | `Decimal(10,2)`, null | как показала площадка |
| `fees_included` | boolean, **null = не выяснено** | **новое**, default `None` |
| `collected_at` | datetime | |
| `source` | `avito` / `realtycalendar` | |
| `status` | `ok` / `failed` / `blocked` / `not_available` / `captcha_overlay` | `captcha_overlay` — **новое** |
| `error_note` | text, blank | |
| `raw_dump_path` | char, blank | |

Ограничения на уровне БД:

1. заполнено ровно одно из `competitor` / `apartment`;
2. `price_kind='listing'` ⇒ `check_in` и `nights` пусты;
3. `price_kind='dated'` **и** `status='ok'` ⇒ `check_in` и `nights` заполнены.

**Поправка 1.** Требование дат у `dated` ослаблено до успешных снимков. Допущение
«дату выбираем мы сами» не обосновано, пока не закрыт вопрос 3: по отчёту фазы 0
даты в блоке `nearest-dates` выбирает площадка. Сбой надо записать в любом случае,
даже когда неизвестно, на какую дату он случился, — иначе неудача исчезает из истории.

Констрейнт про `listing` остаётся жёстким и без оговорок: это прямое следствие
правила «витринную цену нельзя подставить вместо реальной».

Индексы `(competitor, check_in, -collected_at)` и `(apartment, check_in, -collected_at)`.

**Неизменяемость.** `save()` на существующей строке и `delete()` поднимают
исключение.

**Поправка 3.** Дыра с массовым и каскадным удалением закрыта не менеджером,
а `on_delete=PROTECT` на обеих FK снимка. Квартиру или конкурента со снимками
теперь нельзя удалить ничем: ни админкой, ни `queryset.delete()`, ни каскадом —
база не даст. Мягкое удаление через `is_active` остаётся единственным способом
убрать конкурента из работы.

## Шаг 3. `latest_prices(apartment, dates)`

Возвращает готовую для шаблона структуру: строка на квартиру и на каждого
конкурента, в строке — ячейка на каждую дату.

Правила:

- **только `price_kind='dated'`.** Снимки `listing` в сравнение не попадают ни при
  каких условиях. Это главный тест фазы;
- ячейка заполнена, если есть снимок `status='ok'` с непустой `price_per_night`.
  Берётся свежайший по `collected_at`. Не «не старше суток», а последний известный —
  ручного ввода в проекте нет, показывать нечего больше;
- если такого снимка нет, ячейка пустая, а причина берётся из **последнего любого**
  снимка на эту дату (`status` + `error_note`). Нет снимков вовсе — «данных нет»;
- возраст данных считается от `collected_at`; шаблон показывает его, если больше 12 часов.

Реализация: один запрос на горизонт дат, сортировка `(check_in, competitor, -collected_at)`,
схлопывание в Python по первому вхождению. Оконных функций нет — переносимо и
на сотне конкурентов на семь дат это несколько сотен строк.

## Шаг 4. Страница `/apartments/<id>/`

Плотная таблица, серверная отрисовка, Bootstrap 5 с CDN. Без пагинации, без AJAX,
без карточек.

- строки — конкуренты, первой строкой наша квартира с выделением;
- столбцы — даты заезда, их число равно `PRICE_HORIZON_DAYS`;
- в ячейке цена за ночь; если снимку больше 12 часов — под ней возраст;
- **поправка 2:** если `nights > 1`, рядом с ценой пометка «среднее за N ночей».
  При `nights > 1` `price_per_night` — среднее по диапазону, а не цена конкретной
  ночи: выходные внутри диапазона дороже. Менеджер должна видеть, что сравнивает
  усреднённое с точечным. Решение записано в `DECISIONS.md`;
- прочерк вместо цены, причина — в `title` (всплывающая подсказка);
- конкуренты дешевле нас на эту дату подсвечены;
- рядом с именем конкурента ссылка на объявление в новой вкладке и минимальный срок —
  **только если он заполнен**. Пусто — ничего не пишем, двойку не подставляем;
- **сортировка** по цене на выбранную дату: заголовок каждой колонки — ссылка
  `?sort=2026-08-27`. Конкуренты без цены на эту дату уходят вниз. По умолчанию —
  по названию;
- **неактивные конкуренты по умолчанию скрыты**, ссылка «показать неактивных (N)»
  раскрывает их отдельным блоком строк, приглушённых;
- шапка таблицы липкая, шрифт мелкий — чтобы сотня строк оставалась читаемой.

Вёрстку тестами не покрываю (`CLAUDE.md`). Тестом покрою только view: что в контекст
не попала ни одна `listing`-цена.

## Шаг 6. `scripts/seed.py`

3 квартиры, по 4 конкурента, снимки за 3 прошедших дня на горизонт вперёд.
Снимки **и с `nights=1`, и с `nights=2`** — пометка про среднее должна быть видна
на тестовых данных (поправка 2).
Цены 4000–9000 за ночь, выходные дороже на 20–30%, всё в `Decimal`,
ни одного `float`. Фиксированный `random.seed` — данные воспроизводимы.

Заголовки квартир и конкурентов помечены как тестовые: собранные данные и выдумку
нельзя путать даже мельком.

Обязательно кладу в набор:

- снимки `failed`, `blocked`, `captcha_overlay` — без них не видно, как выглядит
  неполная картина;
- конкурента, у которого на дату есть **только** `listing` — в таблице у него обязан
  быть прочерк, а не витринное число. Это живая проверка главного правила;
- конкурента без единого снимка;
- одного неактивного конкурента;
- `fees_included=None` везде — вопрос заказчику задан, ответа нет, и выдумывать
  его seed не станет.

# Поправка постановки: период вместо горизонта (27.08.2026)

Заказчик уточнил, как менеджер работает: она смотрит **произвольный интервал
в будущем** — например, 20–23 сентября, — а не ближайшие даты. Сумму за интервал
делит на число ночей. Это ровно то, что делает `price_per_night`, так что метод
совпадает.

## Что изменилось

**Страница показывает один период, а не окно дат.** Два поля — заезд и выезд,
по умолчанию ближайшие выходные (пятница → воскресенье). Период живёт в адресе
(`?from=&to=`), поэтому переживает сортировку, добавление конкурента и пересылку
ссылки коллеге.

**Одна колонка цены вместо колонки на каждую дату.** Рядом сумма за период
и число ночей: видно, из чего получена цена за ночь. Сортировка стала одной —
по цене (`?sort=price`).

**`latest_prices` ищет снимок по паре (дата заезда, число ночей).** Раньше искал
по одной дате, и снимок на две ночи мог оказаться в ячейке трёхночного периода.
Теперь совпадение точное. Если на ту же дату собран другой период, страница
пишет об этом в подсказке — **без числа**: цена за две ночи не заменяет цену
за три, показывать её здесь нельзя.

**Модель не менялась.** `check_in` + `nights` описывали интервал с самого начала.

**`PRICE_HORIZON_DAYS` остался фоновому сбору** и странице больше не нужен.

## Кнопка живого обновления — как я её вижу (фаза 3)

Место под неё уже занято: она стоит справа от полей периода, сейчас неактивна
и подписана «Появится в фазе 3, когда будет сбор цен».

**Зачем она вообще нужна.** Менеджер смотрит произвольный период, а фоновый сбор
обходит ближайшие даты. Совпадение случайно: чаще всего на выбранный период данных
не окажется вовсе. Без кнопки страница будет показывать прочерки, и польза от неё
сведётся к ближайшей неделе.

**Чего делать нельзя.** Собирать внутри веб-запроса. Пауза 3–6 секунд между
обращениями — это на сотне конкурентов от пяти до десяти минут: запрос отвалится
по таймауту, воркер будет занят, а при нескольких воркерах сбор пойдёт в несколько
потоков и площадка ответит блокировкой. Кнопка не должна ходить в Avito сама.

**Как вижу.** Нажатие пишет строку «просьба собрать»: квартира, период, кто и когда
попросил. Отдельный процесс сбора — тот же, что ходит по расписанию, — видит её
и выполняет ближайшим циклом, обычными паузами и в один поток. Страница после
нажатия честно пишет состояние: «сбор запрошен в 14:32, обычно занимает N минут,
обновите страницу». Никакого AJAX: перезагрузка страницы — то, что менеджер и так
делает.

**Обязательные ограничения**, иначе кнопка становится способом получить блокировку:
- одна просьба на квартиру за раз, повторное нажатие ничего не добавляет;
- пауза между просьбами по одной квартире — не меньше времени полного обхода;
- собираются только активные конкуренты и только выбранный период;
- если просьба не выполнена за разумный срок, страница говорит об этом, а не молчит.

**Что решить до реализации:** сколько живёт непрошенная просьба (сутки?), и что
показывать, когда фоновый сбор уже идёт — ждать его или ставить в очередь.
Это вопросы фазы 3, не сегодняшние.
