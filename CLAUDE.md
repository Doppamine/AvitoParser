# CLAUDE.md

Постоянный контекст проекта. Читается в начале каждой сессии. Не удалять и не переписывать без явной просьбы.

## Что это за проект

Внутренний инструмент для компании, сдающей посуточно около 10 квартир в Москве.

Менеджер три раза в день — утром, днём и вечером — смотрит цены конкурентов на Avito и вручную правит цены своих квартир в стороннем сервисе RealtyCalendar. Сейчас она делает это, открывая десятки вкладок вручную.

Приложение показывает всю картину на одной странице. **Решения о ценах принимает человек.** Приложение ничего не советует, ничего не меняет в RealtyCalendar и не рассчитывает «рекомендованную цену». Любая попытка добавить такую логику — выход за рамки задачи.

Пользователей двое: менеджер и владелица. Интерфейс внутренний, дизайн не важен, важна плотность информации.

## Стек

- Python 3.11+, **Django 5.x**
- SQLite на старте, схема должна без переделок переезжать на PostgreSQL
- Django templates + Bootstrap 5 с CDN. Без сборки фронтенда, без React/Vue, без npm
- Django admin используется как есть для управления справочниками
- Playwright (sync API) для сбора данных — отдельным процессом, не внутри веб-приложения
- pytest + pytest-django

Почему Django, а не FastAPI: задача состоит из CRUD, одной серверной страницы и периодической пакетной задачи. Админка, авторизация, ORM и миграции нужны сразу и есть из коробки. Публичного API нет, асинхронность не даёт выигрыша — сбор идёт отдельным процессом.

## Жёсткие правила

Нарушение любого из них — повод остановиться и спросить, а не решать самостоятельно.

**Деньги — только `Decimal`.** Ни одного `float` в проекте, включая тесты и вспомогательные скрипты. В БД `DecimalField(max_digits=10, decimal_places=2)`.

**Снимки цен неизменяемы.** Каждый сбор создаёт новые строки. Существующие снимки никогда не обновляются и не удаляются, даже при повторном сборе на ту же дату. История нужна с первого дня, хотя в интерфейсе она появится позже.

**Никаких выдуманных данных.** Если цену получить не удалось, в базу пишется снимок со статусом ошибки, а не ноль, не `None` под видом цены и не значение из прошлого раза. Интерфейс показывает прочерк и причину. Подставлять правдоподобные числа вместо отсутствующих — недопустимо.

**Мягкое удаление.** Конкурент помечается `is_active=False`. Снимки сохраняются всегда.

**Сравнение по цене за ночь.** У конкурентов разный минимальный срок проживания: у нас 2 ночи, у многих 3. Итоговые суммы несравнимы. Везде, где идёт сравнение, используется цена за ночь, а минимальный срок показывается рядом.

## Правила работы с Avito

**Не авторизоваться под аккаунтом заказчика.** Все обращения только анонимные, как у обычного посетителя. Ни при каких обстоятельствах не использовать её логин, куки или сессию.

**Не обходить защиту.** Никаких сервисов разгадывания капчи, никакой ротации прокси, никакой подмены отпечатков браузера. Если объявление стабильно не читается — это факт, который фиксируется в отчёте, а не задача для обхода.

**Темп.** Пауза 3–6 секунд между запросами, последовательно, без параллельных потоков. Общий объём — сотни обращений в сутки, не тысячи. Полный горизонт дат собирается раз в сутки ночью, ближайшие даты — три раза в день.

**Сохранять сырые страницы.** Любой сбор пишет HTML в `out/dumps/`. Это и материал для разбора сбоев, и фикстуры для тестов парсера.

## Структура репозитория

```
CLAUDE.md          — этот файл
PHASES.md          — фазы проекта, читать перед началом работы
DECISIONS.md       — принятые решения и их причины, дополнять при новых
PLAN.md            — план текущей фазы, ведёшь ты
PROGRESS.md        — журнал сделанного, ведёшь ты
config/            — настройки Django
monitor/           — основное приложение
scripts/probe.py   — диагностический скрипт фазы 0
out/               — дампы, скриншоты, CSV (в .gitignore)
tests/
```

## Как ты работаешь над фазами

1. Перед началом фазы прочитай `PHASES.md` и напиши `PLAN.md`: разбивка на шаги, что именно будет сделано, какие вопросы остались.
2. Дождись подтверждения плана, потом пиши код.
3. По завершении фазы обнови `PROGRESS.md`: что сделано, что проверено тестами, что осознанно отложено, какие обнаружились проблемы.
4. **Не переходи к следующей фазе без явного разрешения.** Фазы принимаются по одной.
5. Любое решение, влияющее на архитектуру или на бизнес-правила, записывай в `DECISIONS.md` с указанием причины.

## Стиль

- Имена, код, коммиты — на английском. Комментарии, docstring и весь текст интерфейса — на русском.
- Комментируй **почему**, а не что. Комментарий, пересказывающий следующую строку, — мусор.
- Тесты обязательны для бизнес-логики и парсинга. Для вёрстки не нужны.
- Не добавляй зависимости без необходимости. Каждая новая строка в `requirements.txt` должна быть обоснована в `DECISIONS.md`.
- Не пиши «на будущее». Абстракции под гипотетические требования запрещены.

## Чего в проекте не будет

Эти пункты обсуждались с заказчиком и отклонены. Не предлагать и не реализовывать:

- автоматическая простановка цен в RealtyCalendar;
- ручной ввод цен менеджером — заказчик отверг явно, вместо него автоповтор и показ последнего известного значения с меткой времени;
- автоматический поиск конкурентов по адресу — список ведёт менеджер вручную;
- рекомендации по ценам, аналитика, прогнозы;
- роли и права пользователей, регистрация;
- мобильное приложение, уведомления кому-либо кроме разработчика.
